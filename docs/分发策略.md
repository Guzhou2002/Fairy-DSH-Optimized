# 分发策略：为什么"新手友好"不该指望上游

> **本文回答一个问题**：上游那套代码，为什么新手装不上？以及这件事该由谁解决。
> **结论先行**：**"新手友好"是你分发版的卖点，不是上游的义务。** 两条线分开走，别混在一起。
>
> ---
> ⚠️ **2026-09-13 补充：本文第 3 节的 D 方案（含依赖 zip）已被实测取代。**
> 实测证明 `dsh plugin add` **官方命令一步到位**（自动装依赖 + 自动注册 bundle），
> `install.ps1` / `uninstall.ps1` **可以废掉**。
> **请以 `docs\安装机制实测.md` 为准**，本文保留作为"上游定位分析"的背景资料。
> ---

---

## 1. 根因：上游**不是**一个"给终端用户安装"的仓库

上游 `README.md` 自己写得很明白：

> 「Fairy 的 DSH 插件套件（**开源发布候选目录**）。本目录与任何生产环境完全独立，
> 不包含个人会话、日志、密钥、缓存、**`node_modules`** 或完整游戏语料。」

里面记录的**唯一**用法，是给开发者跑测试的：

```sh
DSH_HOME="$PWD/.dsh-test-home" ./scripts/test-isolated.sh
```

### 上游真正的"部署单位"是整个 `profiles/web` 目录

```
profiles/web/pnpm-workspace.yaml
    packages: [.]
    nodeLinker: hoisted
    patchedDependencies:
      dsh-message-edit@0.2.3: patches/dsh-message-edit@0.2.3.patch
      dsh-reasoning-effort@0.6.2: patches/dsh-reasoning-effort@0.6.2.patch
```

也就是说，上游的正确用法是：

```
git clone 整个仓库  →  cd profiles/web  →  pnpm install  →  得到装好 5 个插件的 profile
```

**对开发者：没问题。对 QQ 群里的新手：不可能**（要会 git、会 Node、会 pnpm，还要能连 GitHub + npm 仓库）。

---

## 2. 三个问题要拆开看，别当成一个

| # | 问题 | 谁该解决 | 现状 |
| --- | --- | --- | --- |
| ① | 装完还要**手改 profile 配置**才能注册 | 上游（缺 `dsh.bundle.patch`） | ✅ `pr/cordis-bundle` 已解决 |
| ② | `dsh-fairy-contracts` 写成 `link:../../fairy-contracts`，是**开发期相对链接** | 上游 | ❌ 单包单独安装解析不到 |
| ③ | 5 个包都是 `"private": true`，**没发布到 npm** | 上游 | ❌ 没法 `dsh plugin add <包名>` |

> ⚠️ **注意**：`dsh.bundle.patch` 解决的是「**注册**」，**不解决**「取包 + 装依赖」。
> 这是两码事，不要指望一个 PR 全包。

---

## 3. 四条路线

| 方案 | 做法 | 新手体验 | 上游会收吗 |
| --- | --- | --- | --- |
| **A. 发 npm 包** | 5 个包 + contracts 去掉 `private`，发布到 npm | ⭐⭐⭐⭐⭐ `dsh plugin add dsh-fairy-visual` 真·一条命令 | 需要作者有 npm 账号 + 有意愿 |
| **B. 把 contracts 打进 bundle** | 让 `lib/index.js` 也走打包，而不是原样拷贝 | ⭐⭐⭐ 消灭相对链接，仍是正经 npm 包 | 高（正经工程改进），但**对上游收益为 0** |
| **C. vendor 内联** | 把 contracts 源码复制进各包 `vendor/`，import 改相对路径 | ⭐⭐⭐⭐ 零外部相对依赖 | 低（上游不爱接受"复制源码"） |
| **D. 含依赖 zip** | 打包时把 `node_modules` 一起塞进 zip | ⭐⭐⭐⭐⭐ 解压即用 | 不涉及上游 |

> **A 是唯一能让新手真正做到"一条命令"的路线**，但它需要 B 或 C 作为前提
> （发了 npm 包还带 `link:../../`，装上去就是坏的）。

---

## 4. B 方案实测评估（不值得单独提 PR）

实测数据（`upstream-pull-request\fairy-visual\dsh-fairy-visual`）：

| 项 | 数据 | 说明 |
| --- | --- | --- |
| `lib/index.js` vs `src/index.js` | **MD5 完全一致**（`10B10CA3…`） | `lib/index.js` 是**逐字节拷贝**，没打包 |
| `lib/client.js` | 462,580 字节（= `lib/index.iife.js`） | client 是**真打包**过的 |
| `tsdown.config.ts` | `entry: ['src/client/index.js']` | **只打包 client** |
| `dsh-fairy-contracts` 全包 | 约 **5KB**（`index.js` 960B + `diagnostics.js` 4.1KB） | 要内联的东西极小 |

**技术上很好做**：`tsdown.config.ts` 加一个 `src/index.js` 的 entry（`format: 'esm'`），
再把 build 脚本里那句 `cp src/index.js lib/index.js` 换成用打包产物。

**但不值得做**，因为：

- 上游整仓库使用，`link:../../fairy-contracts` **本来就解析得通** → 对上游收益为 0
- 你有 vendor 内联（C），同样不需要
- 唯一需要它的场景是 **A（发 npm 包）**

**结论**：把 B 记在这里当备查，**不要为了它开 PR**。哪天要推 A 了，B 才是第一步。

---

## 5. 结论：两条线分开走

### 🅰️ 给上游的线（PR 只提一件）
- **已做**：`dsh.bundle.patch` + `cordis.patch.yml`（解决 ①）
- **停止**：A / B / C / D 都别提。上游不会为了"方便下游分发"改自己的仓库定位。

### 🅱️ 给你群友的线（保持现状，别动）
- **C（vendor 内联）+ D（含依赖 zip）** 就是你现在的方案，**这是给新手的最优解**
- 它牺牲"和上游结构一致"，换来"解压就能用"。**这个交换是对的**——你面对的是 QQ 群，不是开发者

### 一句话

> **上游负责写代码，你负责让群友装上。** 这两件事本来就该分开，
> 所以「两边共存」是对的，不用纠结要不要"和上游完全一致"。

```powershell
cd C:\Users\1\.dsh\plugins\Fairy-DSH
$p = '.\upstream-pull-request\fairy-visual\dsh-fairy-visual'

# 1) 验证 lib/index.js 是原样拷贝
Get-FileHash "$p\src\index.js" -Algorithm MD5

# 两个哈希应完全相同

# 2) 看上游的部署单位
Get-Content .\upstream-pull-request\profiles\web\pnpm-workspace.yaml

# 3) 看上游对这套东西的定位

```
