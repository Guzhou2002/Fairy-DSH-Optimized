# DSH 插件形态 vs 独立 Electron 形态 —— 能力对比与迁移评估

> **面向**：Fairy-DSH 作者与整理版维护者
> **目的**：在决定"要不要做独立 Electron 版"之前，先把两种形态的**能力边界**和**迁移成本**说清楚
> **日期**：2026-09-13 ｜ 本文所有数字均为实测，非估计

---

## 0. 一句话结论

**两者不是"新旧版本"的关系，而是"寄生"与"自立"的关系。**

- **DSH 插件版**：寄生在 DSH 的界面与运行时之上，**你的代码是"皮肤"**
- **独立 Electron 版**：自己提供一切运行时，**DSH 反而变成了可选的外部依赖**

而且能力分布是 **三个正交维度**，不是一个轴上的两端 —— 所以中间存在多种可行形态，不必二选一。

---

## 1. 先拆成三个正交维度

大部分人讨论"做成 Electron 应用"时会越聊越乱，因为把三件不同的事混着说：

```
        大脑                  外壳                   皮肤
   ┌────────────┐      ┌───────────────┐      ┌──────────────┐
   │  谁在思考   │      │  窗口从哪来    │      │  长什么样     │
   │  模型/会话/工具│     │  浏览器/Electron│     │  mascot/主题  │
   └────────────┘      └───────────────┘      └──────────────┘
```

| 常听到的说法 | 它实际在说哪个维度 |
| --- | --- |
| "做成 Electron 应用" | **外壳**（换窗口容器） |
| "做成动态壁纸" | **外壳的摆放位置**（贴到桌面层） |
| "做成独立桌宠" | **大脑**（不要 DSH 了） |
| "宠物长什么样" | **皮肤** |

**关键**：这三个维度**互相正交**。换外壳不必换大脑；换大脑也不必换外壳。

---

## 2. 两种形态的完整对比

| 维度 | **DSH 插件版** | **独立 Electron 版** |
| --- | --- | --- |
| **运行宿主** | DSH 宿主进程 + DSH Web UI | 自己写的 Electron 主进程 |
| **界面来源** | **DSH 提供**，插件"贴上去" | **全部自己写** |
| **界面契约** | 依赖 `[data-slot=…]` 等官方 DOM 锚点，**官方一改就静默失效** | 自己定，不存在漂移问题 |
| **现成界面** | 会话列表、输入框、Markdown 渲染、代码高亮、工具调用展示、设置页…… **全部白送** | **全部要自己做** |
| **对话能力** | 模型接入 / 会话管理 / 工具调用 / MCP / 上下文压缩 —— **全部白送** | 自己实现（HTTP 调模型不难，其余是活） |
| **API Key 管理** | DSH 设置页现成 | 自己做 |
| **桌面能力** | ❌ 无（被困在网页里） | ✅ 托盘 / 置顶 / 全局快捷键 / 开机自启 / 多屏 |
| **能否常驻桌面** | ❌ 关掉 DSH 窗口就没了 | ✅ 一直飘着 |
| **能否跨应用悬浮** | ❌ 只能在自己窗口内 | ✅ 全局浮层 |
| **能否做动态壁纸** | ❌ | ✅ |
| **安装方式** | `dsh plugin add <包>` | 安装包（exe / dmg / AppImage） |
| **使用者前提** | 已装 DSH + 有 API Key | 装个包即可（**但仍要有 API Key**） |
| **版本兼容风险** | 跟 DSH 版本走 —— 官方 rc 之间会**删 API**（实例见 §5.3） | 自己控制 |
| **分发渠道** | DSH 插件市场 / 群文件 | 应用商店 / 官网 / 群文件 |
| **冷启动成本** | 必须先把 DSH 跑起来 | 只启动自己 |

## 3. 能力覆盖：用集合看更清楚

```
插件版能做到的  =  DSH 提供的一切
                  ∩  网页这个容器能承载的部分
                  ↓
                  有：对话、工具、MCP、会话、设置页
                  无：托盘、全局浮层、壁纸、跨应用悬浮

独立版能做到的  =  你自己实现的一切
                  ∪  桌面系统能提供的一切
                  ↓
                  有：托盘、全局浮层、壁纸、多屏、开机自启
                  无：DSH 白送的那一整套对话基础设施（除非自己接）
```

**两者的交集 = 那只宠物本身。**

也就是说：**宠物（mascot）这部分代码，是两种形态的共同资产；其余部分各自专属。**

## 4. 四种可行形态（不是二选一）

| # | 形态 | 大脑 | 外壳 | 界面 | 工作量 |
| --- | --- | --- | --- | --- | --- |
| **①** | **现状：DSH 插件** | DSH | 浏览器标签页 | DSH 的 | — |
| **②** | **Electron 套壳** | DSH | Electron 窗口 | DSH 的 | **极小**（1–2 天，插件零改动） |
| **③** | **Electron + 调 DSH** ⭐ | DSH（走本地接口） | Electron | 自己做 | **中**（1–2 周） |
| **④** | **纯独立** | 自己接模型 | Electron | 自己做 | **大**（1–2 个月） |

> **② 的关键事实**：Electron 套壳时，**现有插件一行都不用改**。因为它照旧是"贴在 DSH 网页上"，只不过那网页从浏览器标签页换成了 Electron 窗口。

> **③ 的价值**：把"身体"独立出来（桌面能力全有），"大脑"仍借用 DSH —— 绕开了"自己造一个 AI 应用"这个最大的坑。**前提是 DSH 对外提供可调用的本地接口**（这一点尚待确认）。

## 5. 迁移成本评估（按模块实测）

以 `fairy-visual` 的客户端代码为样本。`src/client/` 总计约 **481KB**。

### 5.1 可直接迁移（低耦合）

| 模块 | 体积 | 说明 |
| --- | --- | --- |
| `mascot-runtime.js` | 34KB | 宠物主体运行时 |
| `mascot-style.js` | 15KB | 宠物样式 |
| `mascot-eye-svg.js` | 9.4KB | 眼睛 SVG |
| `mascot-scale-control.js` | 8.3KB | 大小控制 |
| `mascot-animation-speed-control.js` | 5.6KB | 速度控制 |
| `mascot-effects-svg.js` | 5.0KB | 特效 SVG |
| `mascot-geometry.js` | 2.5KB | 几何 |
| `mascot-motion-clock.js` | 1.5KB | 动画时钟 |
| `mascot-event-scheduler.js` | 1.0KB | 事件调度 |
| `mascot-lifecycle.js` | 0.4KB | 生命周期 |
| `mascot-assets.js` | 0.3KB | 素材 |
| `pointer-drag.js` | 5.8KB | 拖拽 |
| **小计** | **约 89KB（≈17%）** | **与 DSH 无关，可直接搬** |

### 5.2 需要重做（DSH 界面专属，占大头）

| 模块组 | 体积 | 为什么搬不走 |
| --- | --- | --- |
| **`composer-*`**（9 个） | 约 53KB | 全部在**改造 DSH 的输入区** |
| **DSH 界面改造**（20+ 个） | 约 150KB | `dom-adapter` / `dom-observer-manager` / `hero-projection-manager` / `semantic-markers*` / `scrollbars-manager` / 各类 `*-geometry-manager` —— **全部依赖官方 DOM 锚点** |
| **`client/index.js`** | 46KB | 插件入口，需要重写 |
| **`style.js`** | 149KB | 混合体：宠物样式与 DSH 界面样式混在一起，需要拆分 |

### 5.3 已实测的兼容性风险

`@deepseek-ai/dsh-settings` 在两个 rc 之间**删除了 API**：

| 版本 | 导出 |
| --- | --- |
| `0.1.1-rc.2` | `settingsNamespace`、`installSettingsSection`、`deepEqualJson`、…… |
| `0.1.2-rc.1` | 只剩 `SettingsConflictError`、`SettingsProvider`、`redactSecrets` |

`fairy-visual/lib/index.js` 首行即 `import { settingsNamespace } from '@deepseek-ai/dsh-settings';`
→ 这就是为什么插件必须把该依赖 **pin 死并自带一份，不能用 peerDependencies**。

**这类风险是"插件形态"的固有成本**：官方 rc 之间可以删 API，插件只能自己扛。
**独立形态则把这个风险转移到自己手里**（自己定版本、自己控兼容）。

## 6. 结论与建议

### 6.1 两种形态的定位

| | DSH 插件版 | 独立 Electron 版 |
| --- | --- | --- |
| 本质 | **DSH 的皮肤** | **自己的应用** |
| 优势 | 白送全套对话能力；开发成本极低；跟 DSH 生态走 | 完整的桌面能力；不依赖 DSH；版本自控 |
| 劣势 | 被困网页内；界面契约受制于人；rc 之间 API 会变 | 要自己造对话基础设施；分发与更新成本高 |
| 适合 | "想让 DSH 变得好看/好用" | "想让宠物一直待在桌面上" |

### 6.2 建议的推进顺序

**不建议一步跳到纯独立。** 建议按 ②→③→④ 递进，每一步都可单独交付：

1. **② Electron 套壳** —— 极低成本，先验证"桌面容器"这条路通不通
2. **③ Electron + 调 DSH 本地接口** —— 性价比最高；身体独立、大脑借用
3. **④ 纯独立** —— 只在前两步验证过、且确认要脱离 DSH 时再做

### 6.3 共同资产应该抽出来

不论走哪条路，`mascot-*` 那 11 个模块都是**共用资产**。
建议尽早把它们从 `fairy-visual` 里**抽成独立模块**（去掉所有 DSH 依赖），
这样两种形态可以共用同一份宠物实现，而不是各写一套。

## 7. 尚待确认的前提

| # | 问题 | 影响 |
| --- | --- | --- |
| 1 | **DSH 是否对外提供可调用的本地接口？**（`127.0.0.1:3080` 上有没有给第三方用的 API） | 决定形态 ③ 是否可行 —— 这是性价比最高的一条路 |
| 2 | `mascot-*` 模块的实际耦合度（它们 import 了哪些 DSH 的东西） | 决定 §6.3 的"抽成独立模块"有多难 |
| 3 | `style.js` 中宠物样式与 DSH 界面样式的实际比例 | 决定样式部分要拆多久 |
| 4 | 两种形态是否会**长期并存**（插件版继续维护，独立版另起） | 决定代码是"分支"还是"重构" |
