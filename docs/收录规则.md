# 收录到 DSH 插件市场：规则与改造方案

> 调研日期：**2026-09-13** ｜ 数据来源：`awesome-dsh-plugin` 仓库的 `contributing.md` 与 `plugins.json`（实测抓取，非推测）
>
> **一句话结论**：市场**按「单个插件」收录，明确拒绝聚合包**；本项目当前**无法从源码安装**，因此**必须提供预构建 tarball**。

---

## 0. 结论先行（四条最关键）

| # | 结论 | 对本项目的影响 |
| --- | --- | --- |
| 1 | **聚合包不收录** —— "List the plugins, not the bundle" | ❌ 放弃"一个大包 + 一条命令"的设想 |
| 2 | **monorepo 子包可以分别收录**，但**一个 PR 最多 3 条** | 5 个插件要分 2 个 PR；且官方建议**只挑最好的几个** |
| 3 | **"仓库无法从源码安装时，`tarball:` 字段是必需的"** | ⚠️ 正中本项目现状 → **tarball 不再是可选项** |
| 4 | **fork 可以收录**，条件是"维护得更好，或确实做了新东西" | ✅ 本项目确实加了新功能 → 符合，但**必须明确署名橙汁** |

> ⚠️ **目标转换**：原计划是"让仓库结构与上游一致"，**这个目标可以放弃了**。
> 新目标是「**每个插件包自包含、可安装、可收录**」——而 vendor 内联、包内 `.agent-presets/`
> 这些"与上游不一致"的地方，**恰恰是可收录的加分项**。

## 2. 硬要求：CI 依次检查的 4 项

| # | 检查 | 说明 |
| --- | --- | --- |
| 1 | **条目数** | 一个 PR **最多 3 条**，最先检查（早于任何网络请求） |
| 2 | **`dsh.bundle`** | 从仓库 `package.json` 读（**根包，或 `packages/` · `plugins/` · `apps/` 子包**）。**只声明 `dsh.client` 会失败** |
| 3 | **仓库创建满 1 天** | 自动检查，过滤"PR 前几分钟才建好"的仓库 |
| 4 | **`awesome-lint` + 站点构建** | 双语一致性、分隔符、日期、截图 |

### 投稿形式：**一个插件一个 YAML 文件**

路径 `data/plugins/<owner>__<repo>.yml`：

```yaml
url: https://github.com/owner/repo        # 必须与仓库完全一致
name: owner/repo
category: ui
description:
  en: One-line description ending with a period.
  zh: 一句话描述，以句号结尾。            # 可选，维护者会补
```

**只有 `description.en` 必填。** ⚠️ 描述里含 `: `（冒号+空格）**必须加引号**，否则 YAML 解析失败。

> **monorepo 子包**：`url` 指向子目录，`name` 用 `owner/repo#subname`，例如
> `url: https://github.com/owner/repo/tree/main/packages/my-plugin`
> 文件名变成 `owner__repo--packages-my-plugin.yml`

### 可用分类

`agi` `ui` `usage` `theme` `model` `identity` `session` `memory` `tools` `wsl`
`browser` `vision` `voice` `docs` `skill` `workflow` `git` `notify` `dev`
`security` `remote` `market` `fun`

## 3. 评审会实际看什么（8 条）

1. 代码是否与条目声明一致（含描述里的数字、API 名称）
2. 分类是否合理（**不会因此被打回**，维护者直接改）
3. 是否是真实可用的代码（占位/空壳不收）
4. 是否已被现有条目覆盖 —— ⚠️ **"规则不是先来后到，规则是谁更好"**
5. 源码有无可疑之处（混淆、凭据外传、异常安装期行为）
6. PR 是否动了无关条目
7. **是不是纯聚合包** —— ⚠️ 见下
8. **依赖是否指向原作者** —— ⚠️ 见下

### ⚠️ 第 7 条原文（对本项目致命）

> A bundle whose only content is a dependency list — it installs a set of other plugins and ships
> no behaviour of its own — is **not listed as an entry**. **List the plugins, not the bundle.**
> ……`hyzyn/dsh-plugin-kit` 与 `wingsky-1/dsh-plugin-hub` 是可以照抄的形态：
> **两者都发了 all-in-one 包，也都只收录了单个插件。**

### 第 8 条原文

> **Do its dependencies point at the original.** A bundle's dependencies must resolve to the
> original author's repository or their published npm package. Re-uploading other people's plugins
> under your own account and depending on those copies is **not listed**.

### ✅ 但 fork 是可以收录的（第 4 条原文）

> So **a fork *is* added when it is the better-kept one, or when it genuinely adds something.**
> The rule is not first-come; the rule is whichever is better.

**本项目确实"加了新东西"**（设置栏合并、朗读自检、SoVITS 配置、人设一键默认）→ 符合条件。
但**必须明确署名橙汁**，不能伪装原创。

## 4. 🚨 四条直接命中本项目的条款

### ① 聚合包不收录 → 放弃"一条命令装 5 个"

**市场里是逐条收录的**，一个插件一行。你的"一条命令装全部"**只能在自己发的说明里用**。

### ② 一个 PR 最多 3 条，且要"挑"

> If several plugins are yours, **split *and* pick**. Send the ones you would keep if you could only
> keep a few, **not everything that works**.

→ 5 个插件**不要全交**。挑 2–3 个最好的（比如 `dsh-fairy-visual` + `dsh-fairy-voice`）。

### ③ 无法从源码安装 → **`tarball:` 字段是必需的**

> Not publishing to npm? Attach a prebuilt tarball to a GitHub Release and point at it with an
> optional `tarball:` field. **Required if your repo can't be installed from source at all.**

```yaml
tarball: https://github.com/owner/repo/releases/latest/download/your-plugin.tgz
```

> ⚠️ **`latest/download/` 只在请求时解析 `latest`，文件名照字面取。** 资产名带版本号的话，
> 提交当天有效，**下次发版就 404**。要么资产名不带版本，要么钉住 tag。

**本项目的仓库当前就是"无法从源码安装"**（`dsh-fairy-contracts: link:../../fairy-contracts`，
详见 `docs\安装机制实测.md` §3）→ **tarball 是必需品**。

### ④ 官方 `@deepseek-ai/*` 建议用 `peerDependencies`（推荐项，非硬要求）

> Declare official `@deepseek-ai/*` packages as `peerDependencies`, not `dependencies`.

⚠️ **与本项目的已知冲突**：本项目的包把 `@deepseek-ai/dsh-settings` **pin 在 `dependencies: "0.1.1-rc.2"`**，
而 `docs\验证报告.md` §6 明确写：**"该 pin 是插件在当前 DSH 上可用的前提，不可提升或覆盖"**。
→ **改成 peer 会解析到宿主的 `0.1.2-rc.1`，可能直接坏掉。这一条不要盲从，必须实测。**

> 另有一个 prerelease 范围的坑（原文详述）：范围里若没有**与该版本 `major.minor.patch` 元组一致、
> 且自身带预发布标签**的比较符，会**静默排除**所有预发布构建。
> 正确写法：`">=0.0.1-rc.1 <0.1.0 || >=0.1.0-rc.1 <0.2.0-0"`。

## 6. 改造方案

### 🎯 目标转换

| 原目标 | 新目标 |
| --- | --- |
| 让仓库结构与上游（橙汁）保持一致 | **让每个插件包自包含、可安装、可收录** |

**这两个目标方向相反。** 对齐上游要求"人设回仓库根、恢复删除的目录"；
可收录要求"每个包自己带齐东西、能独立打包安装"。**应以后者为准。**

### 分步改造

| 阶段 | 做什么 | 产出 |
| --- | --- | --- |
| **A. 让包真正自包含** | vendor 内联固化到包里（不再依赖 `link:../../`） | 每个包单独拿出来就能装 |
| **B. 产出预构建 tarball** | `pnpm pack` × 5，挂到 GitHub Release | 满足 `tarball:` 必需项 |
| **C. 写收录条目** | `data/plugins/*.yml`，**挑 2–3 个** | 提交 PR |
| **D. 仓库设置** | 打 `dsh-plugin` topic | GitHub 设置 |
| **E. 署名** | README / 描述里明确 fork 自橙汁（Apache-2.0 §4(b)） | 合规 |
| **F. （可选）发 npm** | 免 `allowBuilds` 构建授权 + 显示下载量 | 安装体验更好 |
| **G. （可选）** | 官方包改 `peerDependencies` | 🚫 **实测证明会坏，禁止。见 §7.2** |

> **F 的注意**：已发布 npm 包的 `repository` 字段**必须指回收录的仓库**，否则两者不关联。
> 且**不要**在条目 yml 里手写 `npm:` 字段（会被校验拒绝），映射自动从 registry 采集。

## 7. 实测结论（2026-09-13）

### 7.1 ✅ 目录结构不受限制 —— 本项目的 `fairy-visual/dsh-fairy-visual/` 合规

**方法**：从 `awesome-dsh-plugin` 生成出的 README 中，提取所有指向子目录的条目（URL 含 `/tree/`），统计其一级目录名。

**结果**：共 **389 条** monorepo 子目录条目，一级目录名分布：

| 目录名 | 条数 | | 目录名 | 条数 |
| --- | --- | --- | --- | --- |
| `packages` | 180 | | `adapters` | 6 |
| `plugins` | 64 | | `dsh-plugins` | 4 |
| `plugin` | 19 | | `bundle` | 4 |
| `dsh-plugin` | 12 | | `src` | 3 |
| `integrations` | 11 | | `apps` | 2 |
| `dsh` | 9 | | **其余 50+ 种各 1 条** | 50+ |

其余单例包括 `kit` / `client` / `skins` / `extensions` / `examples` / `dsh-pet` / `dsh-aischat` 等，
以及**三层深**的例子：`.../tree/master/packages/bundle/blue`、`.../tree/main/src/plugins/dsh-plugin-setting-mcp`。

**结论**：**顶层目录名完全自由。** contributing.md 里那句
"root, or a `packages/` · `plugins/` · `apps/` subpackage" 的真实含义是：
**当 `url` 指向仓库根时**，CI 会去这几个常见位置找 `package.json`；
**`url` 直接指向子目录时，CI 就读那个子目录**。

→ ✅ **本项目无需为了收录改任何目录名。**

### 7.2 🚫 官方包改 `peerDependencies` 会直接坏掉 —— 禁止

**背景**：`@deepseek-ai/dsh-settings` 在两个 rc 之间**删掉了 API**。

**实测三方对照**：

| 位置 | 版本 | 导出 |
| --- | --- | --- |
| **插件包内部**（本项目 pin 的那份） | **0.1.1-rc.2** | `settingsNamespace` ✅、`installSettingsSection`、`deepEqualJson`、`SettingsConflictError`、`SettingsProvider`、`redactSecrets` |
| **宿主 `dsh` 安装目录** | **0.1.2-rc.1** | `SettingsConflictError`、`SettingsProvider`、`redactSecrets`、`default` —— ❌ **无 `settingsNamespace`** |
| **live profile** | **0.1.2-rc.1** | 同上，❌ 无 `settingsNamespace` |

而插件 `lib/index.js` 首行就是：

```js
import { settingsNamespace } from '@deepseek-ai/dsh-settings';
```

**推导**：改成 `peerDependencies` → 由消费者（profile）提供 → 解析到 **0.1.2-rc.1**
→ **该版本没有 `settingsNamespace` 这个命名导出**
→ **ESM import 直接失败 → 插件加载崩掉。**

→ 🚫 **这一条绝不能改**，并且要在收录 PR 里**主动说明原因**，
避免评审误以为把官方包放进 `dependencies` 是失误。

**顺带查到**（影响 tarball 方案可行性）：

| 检查 | 结果 |
| --- | --- |
| `@deepseek-ai/dsh-settings` 在 npm 上的版本总数 | 21 |
| `latest` | **0.1.5-rc.2**（远新于本机宿主的 0.1.2-rc.1） |
| **`0.1.1-rc.2` 是否还在 registry** | ✅ **在** —— 所以 tarball 在别人的机器上装得出来 |
