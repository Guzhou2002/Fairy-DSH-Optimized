### 1.1 乱码那件事的结论（重要，别重踩）

- **根因**：`.cmd` 存成 UTF-8 时，中文在 **936 代码页**的系统上会让 `cmd.exe` 认错行尾换行符 →
  `rem` 注释行被从中间切开当命令执行 → 满屏 `is not recognized`
- **判别方法**：`chcp` 显示 **936 = 会中招**；显示 **65001 = 不会**
- **为什么开发机复现不出**：本机是 Win11 且开了全局 UTF-8，ANSI 代码页就是 65001，恰好躲过
- **正确做法**：GBK + 全 CRLF + 无 BOM + 第 2 行 `chcp 936`；不能有 GBK 存不下的字符（emoji）
- 参考实现：同目录的 `verify.cmd` —— 它是**纯 ASCII 启动器**，中文全放 `.ps1` 里

## 2. 🔴 当前唯一的技术待办：语音「消息识别」失败

### 2.1 现象

设置 → Fairy → 朗读功能自检，第 7 项**永远失败**，两份不同机器的诊断 JSON **逐字相同**：

```
hasChat: false      chatKeys: []
orderLength: -1     turnCount: -1
userSeq: 0          finalCount: 0
nodesKind: "undefined"
snapshotKeys: [sessionId, queue, pendingSubmissions, running, subagent, removed,
               openState, openError, hasMore, loadingOlder, promptError, blank,
               lastAgentError, promptAttempted, awaitingFirstTurn]
```

用户已在**有真实对话的会话**里复测过，仍然失败 → 不是"空会话"导致的。

### 2.2 根因（已定位到行）

`fairy-voice\dsh-fairy-voice\lib\client.js`

- **第 1031 行**：`const snapshot = useSession(readVoiceTimeline);`
- **第 455 行**：`function readVoiceTimeline(snapshot)` —— 全程只读 `snapshot.chat.*`
  （`chat.order` / `chat.nodes` / `chat.timeline.turnOrder` / `chat.legacy.*`）

**`useSession` 是 DSH 官方客户端 hook**，它交给插件的快照只有上述 15 个字段，
**根本没有 `chat`**。插件是按更早的 DSH API 写的（`settingsNamespace` 那事也是同一批变化），
DSH 0.1.2-rc.1 换了快照结构，插件没跟上 → 读不到任何消息 → 朗读没内容可读。

### 2.3 正确的改动位置（关键，别改错文件）

两个 `lib\client.js` **都是生成物**，直接改会被下次生成覆盖。**要改生成器**：

**`lib\settings-merge.ps1`**

| 行 | 内容 |
| --- | --- |
| L46 | `function FairyVoicePanel()` —— 自检面板本体 |
| L133 | `} else if (diag.hasChat !== true) {` —— 「消息识别」的失败判定 |
| L533-539 | 诊断通道注入（`globalThis.__FAIRY_VOICE_DIAG__ = {...}`） |

改完必须重新生成：

```powershell
. .\lib\settings-merge.ps1; Set-SettingsMerge -Root (Get-Location) -Mode merged -Snapshot -Force
node --check .\fairy-visual\dsh-fairy-visual\lib\client.js
node --check .\fairy-voice\dsh-fairy-voice\lib\client.js
```

### 2.4 下一步方案（用户已选定 B）

**B = 先看清真实结构，再改适配**（不读 DSH 本体的 `node_modules`，因为用户规矩禁止）

1. 在 **诊断注入处（L533 附近）** 加一个「结构摘要」字段：
   只输出**键名 + 类型**，最多两层，**不含任何内容**（和现有诊断的隐私口径一致）
2. 在 **Fairy 设置面板最底部**（`FairyVoicePanel` 里，用户明确要求的位置）加一层，
   把这份结构摘要显示出来
3. 重新生成 → 用户**重载页面 + 跑一次自检** → 从真实的诊断 JSON 里看
   **`chat` 到底挪哪去了**（比如是不是在 `openState` 里）
4. 据此改 `readVoiceTimeline` 的读取路径

> ⚠️ **红线**：`fairy-voice` 的朗读逻辑不许改。这一步动的是**读消息的适配层**，
> 但仍在 `fairy-voice` 里，所以改动必须加 `[local patch 0.2.x]` 注释，
> 并同步写进 README 的「本地改动」章节。

## 4. 环境与坑（本机）

- DSH `0.1.2-rc.1`、Windows 11 build 26200、Node 24、pnpm 11
- **本机 ANSI 代码页 = 65001**（全局 UTF-8）→ 所以 `.cmd` 编码问题在本机**永远复现不出来**，
  必须靠**另一台 936 的真机**验证
- live profile：`dsh-fairy-visual` / `dsh-fairy-voice` / `dsh-balance-meter` 三个以 **`link:`** 装入
- **git push**：全局配了 `http.https://github.com.proxy = http://127.0.0.1:7897`，但梯子常关。
  **代理不通时直接绕开反而能成功**：
  ```powershell
  git -c "http.https://github.com.proxy=" push origin main
  ```
- **绝不要**在此目录跑 `git clean -fd`（会删掉插件依赖）
- `edit` 工具改 `.ps1` 会**丢掉 BOM**，改完必须补：
  ```powershell
  $t = [IO.File]::ReadAllText($p); [IO.File]::WriteAllText($p, $t, (New-Object Text.UTF8Encoding($true)))
  ```
