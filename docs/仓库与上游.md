# 仓库与上游的关系（fork 维护手册）

> 这份文档回答一件事：**主代码是别人的，我要长期维护自己的优化分支，怎么操作才不会乱。**

## 1. 定位：这是一个 fork，不是原创项目

| 项 | 值 |
| --- | --- |
| 上游仓库 | https://github.com/Chengzhibense/Fairy-DSH |
| 上游作者 | 橙汁本色 |
| 本仓库 | 孤舟蓑笠 的优化分支（整理包 + 安装器 + 本地补丁） |
| 分支基点 | 上游 `main` @ `d639887`（"Fix GitHub Actions pnpm cache paths"） |
| 许可 | Apache-2.0（上游原创代码） |

本地的 `main` 分支**第一个父提交就是上游的 `d639887`**，所以历史上你和上游共享血缘：
`git log` 能追溯到上游的初始提交，将来合并上游更新是一条 `git merge` 的事，不需要"重新粘一遍代码"。

## 2. 三个 remote 的分工

```
origin    → https://github.com/Guzhou2002/Fairy-DSH-Optimized.git   （你的主仓库，对外发布）
myfork    → https://github.com/Guzhou2002/Fairy-DSH.git             （你的备份仓库 / 上游纯净镜像）
upstream  → https://github.com/Chengzhibense/Fairy-DSH.git          （橙汁本色，只读，用来取更新）
```

已经配好了，`git remote -v` 可以看到。

> ⚠️ **`upstream` 的推送地址已焊死**：`git remote set-url --push upstream DISABLED`
> `git remote -v` 里会显示成 `upstream  DISABLED (push)`。
> 这样即使手滑敲了 `git push upstream`，也会被本地当场拦下（`fatal: 'DISABLED' does not appear to be a git repository`），
> **物理上杜绝误推别人的仓库**。拉取**不受影响**，`git fetch upstream` / `git merge upstream/main` 照常可用。
> 若哪天真的需要恢复可推（一般不需要）：
> `git remote set-url --push upstream https://github.com/Chengzhibense/Fairy-DSH.git`

日常只需要：

```powershell
cd C:\Users\1\.dsh\plugins\Fairy-DSH
git push origin main          # 推提交到主仓库
git push origin v0.2.x        # 推标签
```

`myfork` 用来放"准备提给上游的干净分支"（见 `docs\改动清单.md` §6），与主仓库的发布线互不干扰。

> **关于"Fork 标签"**：本仓库是**自建仓库**（不是 GitHub 页面上的 Fork 按钮建的），
> 所以仓库页不会显示"forked from …"字样（`repo.fork = false`）。
> 但**提交血缘是真实的**——你那条提交的父提交就是上游 `d639887`，
> `git merge upstream/main` 照常可用。若你更想要那个官方 Fork 标识，
> 可以去上游页面点一次 Fork，再把同样的内容推上去（两套 remote 可以并存）。

## 3. 日常：把上游的更新合进来

```powershell
cd C:\Users\1\.dsh\plugins\Fairy-DSH

git fetch upstream                 # 只下载，不动你的文件
git log --oneline main..upstream/main   # 先看上游多了什么
git merge upstream/main            # 合进来（更偏好线性历史可以用 rebase）
```

合并后**必须重新生成客户端合并包**，再验证，再提交：

```powershell
. .\lib\settings-merge.ps1
Set-SettingsMerge -Root (Get-Location) -Mode merged -Snapshot -Force
node --check .\fairy-visual\dsh-fairy-visual\lib\client.js
node --check .\fairy-voice\dsh-fairy-voice\lib\client.js
```

## 4. ⚠ 三个"结构性冲突点"（合并上游时一定会遇到）

这是本分支和上游结构不同造成的，**合并前请先读这一段**，否则容易把上游更新悄悄丢掉。

### 4.1 人设预设被移进了插件包

| | 位置 |
| --- | --- |
| 上游 | `.agent-presets/fairy/…`（仓库根） |
| 本分支 | `fairy-visual/dsh-fairy-visual/.agent-presets/fairy/…`（包内） |

**为什么移动**：`dsh plugin add` / npm / tarball 安装时只带一个包目录，预设放在插件包内才能
跟着包一起走（否则装到别的机器就丢了）。根目录 `.agent-presets/README.md` 是指路牌。

**后果**：上游更新人设语料时，git 会报 `deleted by us`（你删了它、它改了它）。
这时**不能"接受删除"就完事**——要手动把上游的新语料同步进插件包：

```powershell
git show upstream/main:.agent-presets/fairy/canon/fairy_canon.json > fairy-visual\dsh-fairy-visual\.agent-presets\fairy\canon\fairy_canon.json
# 其余文件同理，或整体取一次：
git checkout upstream/main -- .agent-presets/fairy
Copy-Item -Recurse -Force .\.agent-presets\fairy\* .\fairy-visual\dsh-fairy-visual\.agent-presets\fairy\
Remove-Item .\.agent-presets\fairy -Recurse -Force   # 根目录只留 README 指路牌
```

> 另外：上游的 `agent.cordis.yml` 里引用了作者私有的 `runtime/index.js` 与 `runtime/safety-gate.js`
> （这两个文件上游没发布），本分支已把这两条移除——同步时**这两条要保留移除状态**，否则预设又加载不了。

### 4.2 客户端 `client.js` 是**生成物**，不是上游原件

| 文件 | 来源 |
| --- | --- |
| `upstream-originals\fairy-visual-client.js` | 上游原件（**只读副本**） |
| `upstream-originals\fairy-voice-client.js` | 上游原件（**只读副本**） |
| `fairy-visual\…\lib\client.js` | 由 `lib/settings-merge.ps1` 生成（含设置栏合并 / 自检面板 / 通知行） |
| `fairy-voice\…\lib\client.js` | 由同一个脚本生成（去掉它自己的 settings.section + 诊断通道） |

**合并上游时最容易犯的错**：直接接受上游对 `lib\client.js` 的改动 —— 那会把你的设置栏补丁覆盖掉。

正确顺序：

1. `git checkout upstream/main -- <该包的 lib/client.js>` **先别直接接受**；
   把上游的新版另存为 `upstream-originals\fairy-visual-client.js`（原件位置）；
2. 重新运行 `Set-SettingsMerge -Mode merged -Force` 生成；
3. `node --check` 两个生成物；
4. 若生成脚本报「锚点匹配数不为 1」→ 说明上游改了结构，需要同步更新 `lib\settings-merge.ps1` 里的锚点。

### 4.3 每个插件包都改过 `package.json` 与 `lib/index.js`

本分支为了"单包可独立分发"做了三件事，合并时不要被上游覆盖回去：

- `dsh-fairy-contracts` 依赖被**内联**进各包 `vendor\`，依赖里删掉了它；
- 依赖布局改为 **hoisted 扁平**（各包 `pnpm-workspace.yaml: nodeLinker: hoisted`），零符号链接；
- 各包新增 `cordis.patch.yml` + `dsh.bundle.patch`，让 `dsh plugin add` 一条命令就能装。

### 4.4 上游有、本分支没有的东西（删除是有意的）

| 上游路径 | 本分支为何不保留 |
| --- | --- |
| `fairy-system/` | 上游的"系统语音"插件，本分支改走 GPT-SoVITS 路线（`docs/` 与 `patches/abandoned/` 有记录） |
| `profiles/`、`scripts/`、`.github/` | 上游的开发脚手架 / CI，本分支是分发仓库 |
| `RELEASE-CHECKLIST.md` | 已由 `UPSTREAM-RELEASE-CHECKLIST.md` + `RELEASE-NOTES.md` 取代 |

需要时可以用 `git checkout upstream/main -- scripts/` 把它们拿回来。

## 5. 分支与发布策略

```
main                你的发布线（永远可打包、可发群）
  ├─ feat/*         新功能（可选，做完合回 main）
  └─ v0.2.3         tag：一个可发布版本
```

发版流程：

1. 改仓库根 **`VERSION`** 文件（整理版版本号，会显示在设置页顶部）；
   **改动了哪些插件包，就把那些包的 `package.json` 的 `version` 往上加** ——
   `install.cmd` 与插件市场都靠「包版本」判断有没有更新；
   再更新 `README.md` / `RELEASE-NOTES.md`；
2. 重新生成客户端合并包（第 3 节命令）；
3. `.\pack.ps1` → 产出 5 个 `.tgz`（文件名**不带版本号**，可直接上传）+ `install.cmd` + `SHA256SUMS.txt`；
4. `.\verify-isolated.ps1` 或 `tools\settings-probe.mjs` 跑一遍实测；
5. `git add -A; git commit -m "release: v0.x …"; git tag v0.x; git push origin main --tags`；
6. 把**不带版本号的那 5 个 `.tgz`** 作为 GitHub Release 附件上传；
7. 群里公告版本号（如 `v0.3.0`），方便群友核对。

> ⚠️ 附件名**必须不带版本号**：README 与 `install.cmd` 里用的是
> `.../releases/latest/download/<包名>.tgz` 这种永久地址，而 `latest/download/` 的文件名是**照字面取**的 ——
> 带版本号的话，提交当天有效，下次发版就 404。
>
> 旧脚本（`install.ps1` / `uninstall.ps1` / `build-release.ps1` / `安装说明.txt` / `patches\`）
> 已全部挪进 `legacy\`，说明见 `legacy\README.md`。

> `release/` 与 `*.zip` 已在 `.gitignore` 里：**不要**把二进制包提交进历史，每次发版都会让仓库膨胀。
> 分发走 GitHub Releases + QQ 群。

### ⚠ Release 附件必须用英文名

**GitHub 会把附件名里的中文吞掉**：`Fairy-DSH-v0.2.3-一键部署版-含依赖.zip` 上传后变成
`Fairy-DSH-v0.2.3-.-.zip`（实测，转义本身是对的，是 GitHub 侧清洗）。所以：

| 附件名（英文，GitHub 用） | 对应群文件（中文） |
| --- | --- |
| `Fairy-DSH-v0.2.x-deploy-with-deps.zip` | `Fairy-DSH-v0.2.x-一键部署版-含依赖.zip` |
| `Fairy-DSH-v0.2.x-lite.zip` | `Fairy-DSH-v0.2.x-一键安装版.zip` |

Release 正文里要写这张对照表，否则群友不知道下哪个。**本地打包文件名照旧用中文**（发给群友的就是那个）。

传给 GitHub 的 `name` 查询参数记得转义，且 PowerShell 里要用 `${url}?name=` 写法
（`$url?name=` 会被当成变量名的一部分）。

## 6. 许可与归属（Apache-2.0 的义务）

上游原创代码是 Apache-2.0，fork 之后必须做到：

- ✅ **保留** `LICENSE`、`NOTICE`、`THIRD_PARTY_NOTICES.md`、`TRADEMARKS.md`（本仓库已保留全部）
- ✅ **标注被修改的文件**：本仓库统一用 `[local patch 0.2.x]` 注释标记每处改动，
  并在 `RELEASE-NOTES.md` / `README.md` 的「本地改动」章节逐条说明——这正是 Apache-2.0 §4(b) 要求的"modified files 提示"
- ✅ **说明来源**：README、设置栏声明行、安装说明都写明"基于橙汁本色大佬源代码的优化分支"
- ❌ **不要**让人误以为是上游官方发布：不要把包名/仓库名伪装成上游，不要暗示上游为你的改动背书
- ❌ **不要**使用上游商标做宣传（见 `TRADEMARKS.md`）

## 7. 提交前自查

```powershell
git status                                  # 只应看到你有意改动的文件
git diff --stat
git check-ignore -v fairy-visual\dsh-fairy-visual\node_modules   # 确认依赖被忽略

# 敏感信息自查：密钥绝不能进仓库
git grep -n -I -E "sk-[A-Za-z0-9]{16,}|api[_-]?key\s*[:=]\s*['\"]" -- ':!*.md' || echo 没有发现明文密钥
```

`~/.dsh/fairy-voice/voice-brain.json`（语音简报 API Key）由使用者在**运行时**自己生成，
不在本仓库内；如果你手动测试过，注意别把它复制进来。

## 8. 一句话总结

- **血缘**：本地 `main` 接在上游 `d639887` 上 → 上游更新用 `git merge upstream/main`；
- **警惕**：`lib/client.js` 是生成物、人设预设被搬进了包内、五个包的 `package.json` 都改过；
- **发版**：zip 走 Release / 群文件，仓库只放源码；
- **归属**：Apache-2.0，保留 LICENSE/NOTICE，标注改动，写明来源。
